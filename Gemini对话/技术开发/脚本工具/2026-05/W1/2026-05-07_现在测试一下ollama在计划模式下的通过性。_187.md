## 现在测试一下ollama在计划模式下的通过性。

这是一个非常棒的测试点。既然你的脚本已经进入了三级优先级（本地 > API > 兜底）的成熟阶段，测试 Ollama 在 Plan Mode（计划模式） 下的表现，本质上是在考察模型对于复杂任务拆解、逻辑预测以及长上下文保持的能力。
由于计划模式下 AI 只“动口不动手”，它是通过生成 README.md 或执行方案来推演逻辑。你可以从以下三个维度进行压力测试：
1. 逻辑一致性测试（The "Logic Anchor" Test）
在计划模式下，给它一个复杂的图标命名变体，看它能否准确预测匹配结果。

测试指令： “我在 Plan Mode 下模拟：如果 icons/ 文件夹里只有 user_profile_filled.svg，而 keyword 是 member，根据你写的 analyze_folder.py 逻辑，计划模式下你预测会发生什么？请给出推演步骤。”
预期表现： 模型应能指出“精确匹配失败” -> “子串匹配失败” -> “模糊匹配（difflib）开始计算”，并能估算出相似度是否达标。

2. 约束边界测试（The "Constraint" Test）
测试 Ollama 在不实际运行代码的情况下，对你代码中“硬约束”的感知力。

测试指令： “计划模式下：如果我把 output_icons/ 设为只读文件夹，你现在的脚本逻辑在处理 Ollama 请求异常（ConnectionError）时，会如何影响整个工作流？请给出改进计划。”
预期表现： 优秀的模型（如 Qwen2.5-Coder 或 DeepSeek）在计划模式下应该能意识到：虽然捕获了网络错误，但没有处理文件系统写入错误，并主动提出增加 try-except OSError 的计划。

3. 跨模式语境传递（Context Carry-over）
这是 Cline/Ollama 配合最关键的一环。

操作方法： 1.  在 Plan Mode 下详细讨论一个新的功能（例如：给图标库增加“自动压缩”功能）。
2.  不要点执行，直接切换到 Act Mode，问它：“现在按照刚才在 Plan 模式里定的方案，只修改代码逻辑，不要改文档。”
测试重点： 观察 Ollama 是否丢失了刚才在计划模式里确定的“极简精密”设计风格或特定的压缩参数。

调低 Temperature： 将 Ollama 配置中的 temperature 设为 0，强制它进行确定性推理。
模型建议： 如果本地显存允许（12B 及以上），推荐使用 qwen2.5-coder:14b 或 gemma3:12b 进行计划测试，它们对结构化指令（Structured Output）的通过性目前是本地模型中的第一梯队。
